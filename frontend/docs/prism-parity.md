## Visual and selector rules

Preserve the light primary `#3a3a8c`, neutral semantic roles, small control heights and restrained borders. Prism's cool-gray numeric direction differs from conventional Tailwind scales; map meaning rather than copying numeric token assumptions. Inter and JetBrains Mono are reference fonts; local fallbacks remain an explicit difference unless assets are supplied. Generated utility strings, hashed asset names and `radix-:…` IDs are unsuitable public component contracts.

Use accessible role/name for interactions, stable feature hooks for owner boundaries, and explicit DOM IDs only where confirmed. Scope repeated filter/legend hooks to their feature. Keep primitives free of fetching/authentication, domain state in feature owners, and third-party editor internals behind adapters. Billing, Stripe, checkout, subscriptions and Clerk are outside this implementation.

## Server-backed dashboard scope (2026-10-10)

`/dashboards` and `/dashboards/:id` use the same server documents as classic. Lists include search, All/Mine/Favourites, tags, sort and 25-row pagination. Owners edit full documents with a fresh-GET `modified` conflict dialog; admins can delete another owner's dashboard but cannot PUT it. Non-owners get a read-only note. Demo state is per-client memory; old local dashboards have a live-only import notice with explicit removal.

SQL `code`, stored-SQL `builder` and PromQL tiles render through shared query controls; the editor writes classic `chartQuery`, `dbName`, aligned `promqlQueryType`, config, finite grid layout and tile ULIDs. Six variable types and classic interpolation use URL-only selections; unknown dollar tokens remain untouched and only defined variables gate queries or participate in dependency cycles. Time range is dashboard-specific and persists in classic form on Save. ID repair stays separate from user edits, with an owner-only next-save notice and fresh IDs on Duplicate. Tile moves follow the displayed compacted reading order; chart axis titles precede scrollable legends, and variable errors keep controls aligned. Import/export, query viewing, exploration and concrete Create alert links are implemented. Unknown top-level/tile/config fields, Report type, variables, sections and sectionId are retained.

This scope establishes document interchangeability, not pixel parity. Every chart type classic stores renders natively (see the chart renderer scope below); unknown tile and chart types display named placeholders, without a classic fallback link. Import and Duplicate preserve `dashboardType`, including creating copies of Reports. The Create form makes Dashboard documents. Sections render in classic order with independent vertically compacted grids; section authoring, reordering, collapsing, tile drag/resize, present mode, PNG export and auto-refresh are implemented (see the current README). AI, Enterprise/pricing, templates/CDN and visual builder authoring remain excluded. UTC remains the custom time editor's timezone. Relative ranges stay anchored until a range change or Refresh, matching classic. Interrupted local-import batches and attribution of browser-local copies to individual accounts remain follow-ups. Actual test outcomes and the classic render capture are recorded in [Dashboards validation](validation-review.md#dashboards-validation-2026-10-10).

## Dashboard chart renderers (2026-10-11)

Native tiles now draw every chart type classic's editor offers (Timeseries, Line, Bar, Stacked bar, Area, Pie, Donut, Query value, Gauge, Table) plus a native bubble chart, from the same stored documents. Classic draws its tiles with Chart.js; native uses uPlot for cartesian charts and SVG for pie, donut, gauge and bubble, matching the behaviour rather than the library. Stored keys and their meaning are listed in [API contracts](api-contracts.md). A dashboard built through the classic editor, one tile per type, renders all ten tiles in both UIs from the same server.

Intentional differences: timestamp x values keep a time axis in ascending order (classic draws builder buckets in server order on a category axis); y-axis titles sit above vertical charts; units keep a leading space; gauge tracks are slightly darker and yellow query values use a darker yellow for contrast; small pie tiles hide overlapping labels; query-value sparklines need timestamp rows in the tile's own SQL result (classic runs a separate bucketed query); bubble is a native extension with `config.axes.size.field`, which classic's importer strips, and is unavailable for PromQL. Classic quirks are not copied: its PromQL table renders empty, and its `!=".*"` rewrite produces an invalid operator.

## Dataset management scope (2026-10-11)

`/datasets` supports creating logs, metrics and traces, with optional custom partition creation, and deleting datasets after exact-name confirmation. A Manage sheet keeps overview information, current/lifetime/deleted ingestion and storage statistics, schema fields and explorer navigation, retention, hot tier and a Danger zone together. Retention is a single delete task for 1–36,500 days; clearing sends `[]`. Hot-tier allocation, resizing and disabling use the configured server's API with a 10 GiB minimum. Missing server hot-tier configuration is explained without exposing its raw error; a missing per-dataset allocation still permits enabling it. Authorization is evaluated by the server for each action and failures remain in their section or dialog.

Creation sends `X-P-Telemetry-Type` and optional `X-P-Custom-Partition`, with no schema body. Time partitions cannot be set at creation; Overview still displays time partitions reported by existing datasets. Created and latest-event timestamps use the app’s UTC date-time format, with the raw ISO value in a title attribute. The live lifecycle spec verifies creation and the custom partition through the API, retention set/clear, hot-tier availability and typed deletion. The list endpoint returns names only; confirmed telemetry and partition metadata are shown in Overview.

Static schema upload, dataset tags/labels, editing existing partition settings and index management remain excluded. No client permission model is inferred from roles. Demo state is per-client memory and does not persist across reloads. Browser and live specs are authored for the reviewer's shared-lock runs; this change's local validation covers formatting, TypeScript (including both specs) and unit tests.

## SQL workspace scope (2026-10-11)

`/sql-editor` supports adding, renaming and closing query tabs. Each tab owns its SQL, time range, selected datasets, request state, result rows, visible columns, wrapping, output view and chart configuration. Requests may run in separate tabs concurrently; switching tabs does not redirect a response into the active tab. Cancel and close abort the tab’s request, Undo close restores the most recently closed draft, and a session change clears the mounted workspace and result data. The Logs/dashboard query URL handoff remains supported and adds or focuses the incoming query after restoring existing drafts, without replacing the library of drafts. Repeated handoffs with the same SQL and range focus an existing tab. The query/start/end/range parameters are consumed after processing so reloading edited SQL does not reapply an old handoff. The editor preserves Ctrl/Cmd+Enter execution. Sidebar and editor/result split handles support pointer dragging and keyboard resizing; narrow screens stack the panels.

The dataset explorer offers search, multiple dataset selection and schema-field insertion. “New query from selection” opens a separate tab and preserves the current editor. Multiple datasets generate a quoted `UNION ALL BY NAME` source with ordering and `LIMIT 100` applied to the combined rows. BY NAME aligns columns by name and fills missing columns with NULL. Common columns need compatible types; the UI does not infer joins or resolve incompatible types. Demo SQL does not execute unions. The 100-row generated default remains an intentional difference from the static Prism 500-row default.

The saved-query library stores named SQL, time ranges, selected datasets and supported chart configuration. Saved queries use persistent browser local storage. Draft workspaces use browser session storage, independent per browser tab and retained across navigation/reload for that session. Both are scoped to the server origin and signed-in user, with an independent demo scope. Live persistence waits for a known identity and preserves edits made while the initial identity response is loading. An unchanged URL handoff matching a stored draft restores its saved name, dataset selection and chart configuration; explicit anonymous edits remain intact. Draft writes flush on navigation/reload as well as after the editing debounce. Reopening a saved query that already has a tab focuses its existing draft without replacing unsaved edits. Browser queries do not sync to Parseable or another browser, and draft persistence does not store query results. Classic server-saved SQL queries and SQL Logs views appear in a separate read-only “Server saved queries” list, scoped by the account's existing `/filters` authorization; they open as drafts or copy into the browser library without changing the server record. Classic Logs views without a native explorer state can open their stored SQL in the SQL editor; builder and search views remain unavailable rather than being translated. Unsupported stored chart configurations fall back to the default configuration.

Results retain the shared column picker, sorting, pagination, wrapping, event details and JSON/CSV exports. Chart mode uses the existing dashboard renderer, field bindings and appearance controls. Its preview and saved tile use the executed SQL, even when the editor has since changed; the preview uses captured execution bounds. “Add to Dashboard” creates a classic-compatible SQL tile and either creates a dashboard or appends it to an editable existing dashboard. Existing dashboard documents and their time range are preserved, with ownership and conflict checks; a newly created dashboard uses the executed range. Thus an existing dashboard may render different data from the SQL preview.

This scope records implementation behavior, not a claim of full runtime or pixel parity with Prism. SQL AI assistance, server-synced saved libraries, inferred joins and automatic resolution of incompatible column types remain excluded. Validation evidence belongs in [validation review](validation-review.md).
